# How Authentication Works in This App — Backend to Frontend

A complete walkthrough of the auth flow: from a click in the browser, through
Next.js, Arcjet, Better Auth, Drizzle/PostgreSQL, and back — including cookies,
sessions, emails, OAuth, password reset, and every error path.

> Written against the code in this repo: Next.js 16.4, React 19,
> `better-auth` 1.7.15, Drizzle ORM 0.45, PostgreSQL 17.
> If an API differs in another version, check the official docs.

---

## 1. The players

| File | Role |
|---|---|
| `src/lib/auth.ts` | Server-side Better Auth instance: providers, verification, password reset, account linking, session cache. |
| `src/lib/auth-client.ts` | Browser client (`createAuthClient()`), talks to `/api/auth/*` on the same origin. |
| `src/app/api/auth/[...all]/route.ts` | The only auth HTTP entry point. Wraps Better Auth in Arcjet and exports `GET` / `POST`. |
| `src/proxy.ts` | Next.js 16 Proxy (formerly middleware). Redirects logged-in users away from `/auth/login`. |
| `src/db/index.ts` | Drizzle client with the auth schema. |
| `src/db/schema/auth-schema.ts` | Generated tables: `user`, `session`, `account`, `verification`. |
| `src/lib/email.ts` | nodemailer transport → Mailpit (dev) / Postal or SMTP provider (prod). |
| `src/components/auth-tabs.tsx` | Sign in / sign up / forgot password UI. |
| `src/app/reset-password/*` | Set-new-password page. |
| `src/app/page.tsx` | Server component that reads the session and renders sign in / sign out. |
| `src/components/sign-out-button.tsx` | Client sign-out. |

One sentence: **the browser never talks to the database directly.** It calls
`/api/auth/*`; that route runs Arcjet, then Better Auth, which uses Drizzle to
read/write Postgres and sets HttpOnly cookies.

## 2. The 30-second overview

```
┌──────────────┐   fetch /api/auth/*        ┌──────────────────────────────┐
│   Browser    │ ─────────────────────────► │ Next.js route handler        │
│ authClient   │                            │ 1. Arcjet (POST only)        │
│ (React)      │ ◄───────────────────────── │ 2. Better Auth handler       │
└──────────────┘   JSON + Set-Cookie        │ 3. Drizzle adapter           │
       │                                    └──────────────┬───────────────┘
       │                                                   │ SQL
       │                                                   ▼
       │                                        ┌─────────────────────┐
       │                                        │ PostgreSQL          │
       │                                        │ user/session/...    │
       │                                        └─────────────────────┘
       │
       │  HttpOnly cookies: better-auth.session_token (+ session_data)
       ▼
  Server components call auth.api.getSession({ headers })
```

Key idea: **the session is a database row plus a signed cookie.** The cookie
holds an opaque token; the database holds the real session. A short-lived
`session_data` cookie caches the session for 60 seconds.

## 3. Configuration and bootstrapping

### 3.1 Environment

```dotenv
DATABASE_URL=postgresql://postgres:password@localhost:5432/better_auth_tutorial
BETTER_AUTH_SECRET=<32+ random chars>
BETTER_AUTH_URL=http://localhost:3000
```

- `BETTER_AUTH_SECRET` signs cookies, session tokens, and verification JWTs.
  Missing → Better Auth throws at startup in production.
- `BETTER_AUTH_URL` becomes `baseURL`; it is also the **only default trusted
  origin**. Wrong value → OAuth redirects and cookies break.
- In production `BETTER_AUTH_URL` must be `https://...`; Better Auth then uses
  the `__Secure-` cookie prefix and `Secure` cookies.

### 3.2 The auth instance

`src/lib/auth.ts` (abridged):

```ts
export const auth = betterAuth({
  emailAndPassword: {
    enabled: true,
    requireEmailVerification: true,
    resetPasswordTokenExpiresIn: 3600,
    sendResetPassword: async ({ user, url }) => {
      void sendEmail({ to: user.email, subject: "Reset your password", html: `...` });
    },
  },
  emailVerification: {
    sendOnSignUp: true,
    sendOnSignIn: true,
    autoSignInAfterVerification: true,
    sendVerificationEmail: async ({ user, url }) => {
      void sendEmail({ to: user.email, subject: "Verify your email address", html: `...` });
    },
  },
  session: { cookieCache: { enabled: true, maxAge: 60 } },
  socialProviders: { github: {...}, discord: {...} },
  account: { accountLinking: { enabled: true, trustedProviders: ["github", "discord"] } },
  plugins: [nextCookies()],           // MUST be last
  database: drizzleAdapter(db, { provider: "pg", schema }),
});
```

What matters:

| Option | Effect |
|---|---|
| `requireEmailVerification` | A password user cannot sign in until `emailVerified = true` (403). Also makes sign-up return a **generic** response (see §7.1). |
| `sendOnSignUp` | Send the verification email immediately after sign-up. |
| `sendOnSignIn` | Re-send the email when an unverified user tries to sign in. |
| `autoSignInAfterVerification` | Clicking the link creates a session automatically. |
| `cookieCache.maxAge: 60` | `getSession` can answer from a cookie for 60 s without hitting the DB. |
| `trustedProviders` | Only these providers may auto-link to an existing account. |
| `nextCookies()` last | Lets Better Auth write cookies through Next's `cookies()` in server actions/RSC. If it is not last, its hooks run before other plugins and cookies can be lost. |

### 3.3 The database adapter

```ts
database: drizzleAdapter(db, { provider: "pg", schema })
```

`src/db/index.ts`:

```ts
export const db = drizzle(process.env.DATABASE_URL!, { schema });
```

The adapter maps Better Auth models to the generated tables:

| Better Auth model | Table | Holds |
|---|---|---|
| `user` | `user` | id, name, email (unique), `email_verified`, image, timestamps |
| `session` | `session` | id, token (unique), `expires_at`, ip, user agent, `user_id` |
| `account` | `account` | provider (`credential`, `github`, `discord`), provider account id, **password hash**, OAuth tokens |
| `verification` | `verification` | short-lived verification records |

Important: **password users have one `user` row and one `account` row with
`provider_id = 'credential'`.** OAuth users get one `account` row per provider.
That is what makes account linking work.

## 4. Cookies and sessions

### 4.1 The cookies

| Cookie | Contents | Lifetime | Flags |
|---|---|---|---|
| `better-auth.session_token` | signed opaque session token | 7 days (default `session.expiresIn`) | `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` in prod |
| `better-auth.session_data` | compact HMAC-signed session cache | 60 s (`cookieCache.maxAge`) | same |
| `__Secure-better-auth.*` | same, with prefix | — | added when base URL is HTTPS / production |

- The session token cookie is **signed with `BETTER_AUTH_SECRET`**, so it cannot
  be forged. It is also `HttpOnly`, so JavaScript cannot read it (XSS cannot
  steal it directly).
- `session_data` is only a cache. If it is missing/expired, Better Auth falls
  back to the database.
- `dont_remember` and `account_data` cookies exist in Better Auth, but this app
  does not use "remember me" or the account cookie.

### 4.2 Session lifecycle

1. Sign-in/sign-up/OAuth/verification creates a row in `session`
   (`token`, `expires_at`, `user_id`, IP, user agent).
2. Better Auth sets the signed `session_token` cookie and a 60 s
   `session_data` cache cookie.
3. Every `getSession` checks the cache first; on a miss it looks up the token
   in `session`, checks expiry, loads the user, and refreshes the cache.
4. Sign-out deletes the row and clears both cookies.
5. Deleting a user removes their sessions. Password reset only revokes
   sessions when `emailAndPassword.revokeSessionsOnPasswordReset` is enabled
   (it is not set in this app).

### 4.3 Where sessions are read

Server component (`src/app/page.tsx`):

```tsx
const session = await auth.api.getSession({ headers: await headers() });
```

- With `cacheComponents: true`, reading request headers is dynamic, so the
  component must be inside `<Suspense>` — that is why `AuthActions` is wrapped.
- Server actions and route handlers use the same call.
- Client components can use `authClient.useSession()` (not used here yet).

Proxy (`src/proxy.ts`):

```ts
export async function proxy(request: NextRequest) {
  const session = await auth.api.getSession({ headers: request.headers });
  if (session) return NextResponse.redirect(new URL("/", request.url));
  return NextResponse.next();
}
export const config = { matcher: ["/auth/login"] };
```

- Next.js 16 renamed Middleware to **Proxy**; same behavior.
- It runs only for `/auth/login`, using the request's own headers (there is no
  `next/headers()` request scope in Proxy).
- It validates the session, not just "a cookie exists", so expired cookies do
  not lock users out.
- Proxy is an optimistic check only — never the only authorization layer.

## 5. The HTTP surface

Everything goes through `src/app/api/auth/[...all]/route.ts`:

```ts
const authHandlers = toNextJsHandler(auth);
export const { GET } = authHandlers;

export async function POST(request: Request) {
  const decision = await checkArcjet(request);
  if (decision.isDenied()) { /* 429 / 400 / 403 */ }
  return authHandlers.POST(request);
}
```

- `toNextJsHandler(auth)` returns handlers for `GET`, `POST`, `PATCH`, `PUT`,
  `DELETE`. This app exports only `GET` and `POST`.
- `basePath` defaults to `/api/auth`, so the endpoints are:

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/auth/sign-up/email` | Create account |
| POST | `/api/auth/sign-in/email` | Password sign-in |
| POST | `/api/auth/sign-in/social` | Start OAuth |
| GET | `/api/auth/callback/:provider` | OAuth callback |
| POST | `/api/auth/sign-out` | Destroy session |
| GET | `/api/auth/get-session` | Read session (client hook) |
| POST | `/api/auth/send-verification-email` | Resend verification |
| GET | `/api/auth/verify-email` | Consume verification link |
| POST | `/api/auth/request-password-reset` | Send reset email |
| POST | `/api/auth/reset-password` | Set new password |
| GET | `/api/auth/ok` | Health check |

### 5.1 The Arcjet gate

Only **POST** is wrapped. `GET` (OAuth callback, verify link, health) goes
straight to Better Auth.

`checkArcjet`:

1. Clones the request and reads the JSON body (`request.clone()`), so the
   original body is still available to Better Auth.
2. Resolves an identity: session user id, else client IP, else `127.0.0.1`.
3. Applies different rules per path:
   - `/sign-up/email`: `protectSignup` (email validation + bot + strict rate
     limit `10 / 10m`).
   - everything else: `detectBot` + `slidingWindow` (`60 / 1m`).
4. `shield({ mode: "LIVE" })` is always on.

Response mapping:

| Decision | Status |
|---|---|
| rate limit | `429` (empty body) |
| email rule | `400` + `{ message }` (`INVALID`, `DISPOSABLE`, `NO_MX_RECORDS`) |
| bot / shield | `403` (empty body) |
| allowed | request continues to Better Auth |

Consequence: **a `403` with no JSON body means Arcjet blocked the request**,
not Better Auth. A `403` with `{ "message": ... }` is usually Better Auth.

## 6. Frontend: the auth UI

### 6.1 Client setup

`src/lib/auth-client.ts`:

```ts
import { createAuthClient } from "better-auth/react";
export const authClient = createAuthClient();
```

No `baseURL` → same origin, so the client calls `/api/auth/*` on
`http://localhost:3000`. If the API were on another origin, pass `baseURL`.

### 6.2 Pages

| Route | Rendering | What happens |
|---|---|---|
| `/auth/login` | Server page + client `AuthTabs` | Tabs: Sign In / Sign Up. Proxy redirects logged-in users away. |
| `/reset-password` | Server page + client form | Reads `?token=` and calls `resetPassword`. |
| `/` | Server component | Reads the session; shows "Sign in" or "Signed in as … / Sign out". |

### 6.3 Validation and UX

`auth-tabs.tsx` uses React Hook Form + Zod **before** any network call:

- Sign up: name ≥ 2, valid email, password ≥ 8 with uppercase + number,
  confirm matches.
- Sign in: email + password required.
- Forgot: valid email.

Invalid input never reaches the server. Server errors are shown both inline
(`setError("root")`) and as a toast, and the form shakes (GSAP).

## 7. Flow A — Sign up with email and password

```
User fills form
   │  (RHF + Zod validate locally)
   ▼
authClient.signUp.email({ name, email, password, callbackURL: "/" })
   │  POST /api/auth/sign-up/email
   ▼
Arcjet protectSignup  ── denied ──► 400/403/429 → toast + inline error
   │ allowed
   ▼
Better Auth sign-up handler
   │ 1. validate email/password
   │ 2. find user by email
   │ 3. create user (email_verified = false)
   │ 4. create account row (provider_id = "credential",
   │    password = scrypt hash)
   │ 5. requireEmailVerification → NO session, token: null
   │ 6. sendVerificationEmail (sendOnSignUp)
   ▼
sendEmail() → nodemailer → SMTP → Mailpit (dev) / provider (prod)
   │
   ▼
200 { token: null, user: { emailVerified: false, ... } }
   │
   ▼
UI shows "Check your email" (VerifyEmailNotice) + Resend button
```

Important details:

- **No session is created** because the email is not verified. `token` is
  `null`. That is why the UI must not redirect to `/` after sign-up.
- The password is hashed with **scrypt** (Node's `crypto.scrypt`), never stored
  in plain text.
- The verification email contains a link like:

  ```
  http://localhost:3000/api/auth/verify-email?token=<JWT>&callbackURL=%2F
  ```

- The token is a **signed HS256 JWT** (`email`, `exp`) using
  `BETTER_AUTH_SECRET`; default lifetime is 1 hour.

### 7.1 The "existing email" behavior (important)

With `requireEmailVerification: true`, Better Auth deliberately hides whether
an email already exists:

- Sign-up with an existing email returns **`200 OK` with a synthetic user
  object** (a random id, `emailVerified: false`) and **sends no email**.
- The database is **not** modified.

So the UI can say "Check your email" while nothing was sent. To test properly,
always sign up with a **brand-new** email address. Verify with:

```bash
docker compose exec db psql -U postgres -d better_auth_tutorial \
  -c 'SELECT email, email_verified, created_at FROM "user" ORDER BY created_at DESC;'
```

- New row → email was sent (check Mailpit).
- No new row → you reused an email, or the request was blocked before Better
  Auth (Arcjet).

## 8. Flow B — Email verification

```
User clicks link in email
   │  GET /api/auth/verify-email?token=<JWT>&callbackURL=%2F
   ▼
Better Auth verify-email handler
   │ 1. jwtVerify(token, BETTER_AUTH_SECRET, HS256)
   │    ├─ expired  → redirect callbackURL?error=TOKEN_EXPIRED
   │    └─ invalid  → redirect callbackURL?error=INVALID_TOKEN
   │ 2. find user by email from JWT payload
   │ 3. UPDATE "user" SET email_verified = true
   │ 4. autoSignInAfterVerification
   │    → create session row + set cookies
   ▼
302 redirect to callbackURL ("/")
   │
   ▼
Home page server component sees the session
```

- The token is **not** looked up in the `verification` table for this flow; it
  is a self-contained signed JWT. `verification` is used for other short-lived
  records.
- If the link is opened while already signed in as a different user, Better
  Auth handles the session carefully; the safe pattern is to verify in the same
  browser that signed up.
- After verification the user is signed in automatically
  (`autoSignInAfterVerification`), so they land on `/` authenticated.

## 9. Flow C — Sign in with email and password

```
authClient.signIn.email({ email, password, callbackURL: "/" })
   │  POST /api/auth/sign-in/email
   ▼
Arcjet (bot + 60/min)
   ▼
Better Auth sign-in handler
   │ 1. find user + credential account
   │ 2. verify scrypt hash
   │ 3. requireEmailVerification && !emailVerified ?
   │      → sendOnSignIn → send a new verification email
   │      → 403 EMAIL_NOT_VERIFIED
   │ 4. create session row
   │ 5. set signed session cookies
   ▼
200 { token, user }
   │
   ▼
onSuccess: toast + router.push("/") + router.refresh()
   ▼
Home server component reads the session
```

Client error handling (`auth-tabs.tsx`):

| Status | Meaning | UI |
|---|---|---|
| `403` | Email not verified | "Please verify your email first. We sent you a new link." |
| `401` | Wrong email/password | Better Auth's message (`Invalid email or password`) |
| `429` | Arcjet rate limit | Generic error toast |
| `400` | Arcjet email rule | The returned message |

`router.refresh()` matters: the home page is a server component, so the client
must ask Next to re-render it with the new cookie.

## 10. Flow D — OAuth (GitHub / Discord)

```
authClient.signIn.social({ provider: "github", callbackURL: "/" })
   │  POST /api/auth/sign-in/social
   ▼
Better Auth returns { url: "https://github.com/login/oauth/authorize?..." }
   │
   ▼
Browser redirects to the provider
   │  user consents
   ▼
Provider redirects to
   GET /api/auth/callback/github?code=...&state=...
   │  (GET bypasses Arcjet)
   ▼
Better Auth:
   │ 1. validate state
   │ 2. exchange code for access token
   │ 3. fetch the provider profile (email, name, avatar)
   │ 4. find user by email
   │      ├─ none → create user + account row
   │      └─ exists → link this provider to that user
   │ 5. create session + cookies
   ▼
302 to callbackURL ("/")
```

### 10.1 Account linking rules

Auto-linking is allowed only when **both** are true:

1. The provider is in `account.accountLinking.trustedProviders`
   (`github`, `discord` here).
2. The existing local user has `emailVerified = true`.

If a password user never verified their email, linking is refused with
`account_not_linked`. Fix by verifying the email first (or, in development
only, `UPDATE "user" SET email_verified = true;`).

### 10.2 Callback URLs

The callback path is fixed by Better Auth:
`/api/auth/callback/github` and `/api/auth/callback/discord`.

Register exactly that URL in each provider's dashboard, with the same scheme,
host, port, and no trailing slash. `BETTER_AUTH_URL` must match the URL you
actually run on, or redirects go to the wrong host.

### 10.3 `trustedOrigins`

This app does not set `trustedOrigins` explicitly, so Better Auth trusts only
the `baseURL` origin. That is fine locally (`http://localhost:3000`). In
production add every real origin:

```ts
trustedOrigins: ["https://yourdomain.com", "https://www.yourdomain.com"],
```

Otherwise OAuth callbacks and POSTs from another origin get
`403 Invalid origin`.

## 11. Flow E — Forgot and reset password

```
/auth/login → "Forgot password?"
   │ authClient.requestPasswordReset({ email, redirectTo: "/reset-password" })
   │  POST /api/auth/request-password-reset
   ▼
Better Auth:
   │ 1. find user by email (or not)
   │ 2. if missing → fake work + generic success (timing-safe, no enumeration)
   │ 3. create a verification row:
   │      identifier = "reset-password:<random token>"
   │      value      = user id
   │      expires_at = now + 1 h (resetPasswordTokenExpiresIn)
   │ 4. sendResetPassword({ user, url }) with:
   │      /api/auth/reset-password/<token>?callbackURL=%2Freset-password
   ▼
sendEmail() → link in the email
   │
   ▼
UI always shows "If an account exists, we sent a link."
   │
   ▼
User clicks the link
   │ GET /api/auth/reset-password/<token>?callbackURL=/reset-password
   │ 1. look up "reset-password:<token>" in verification
   │ 2. valid   → 302 /reset-password?token=<token>
   │    invalid → 302 /reset-password?error=INVALID_TOKEN
   ▼
ResetPasswordForm reads the token from useSearchParams
   │ Zod: 8+ chars, uppercase, number, confirm matches
   ▼
authClient.resetPassword({ newPassword, token })
   │  POST /api/auth/reset-password
   ▼
Better Auth:
   │ 1. look up the verification row and check expiry
   │ 2. consume the single-use token
   │ 3. update account.password (new scrypt hash)
   │ 4. revoke sessions only if revokeSessionsOnPasswordReset is on
   ▼
200 → toast + router.push("/") → sign in with the new password
```

Notes:

- Unlike email verification, the reset token is **not a JWT**. It is a random
  24-character id stored in the `verification` table and is single-use.
- The form handles `?error=INVALID_TOKEN` (and a missing token) by showing a
  "Link expired or invalid" card.
- Because the request endpoint always succeeds, the UI must not claim that an
  account exists — it says "**If** an account exists…".
- Password reset does **not** require email verification; possessing the
  emailed token is the proof.
- Sessions are **not** revoked by default after a reset. Set
  `emailAndPassword.revokeSessionsOnPasswordReset: true` if you want that.

## 12. Flow F — Sign out

```
SignOutButton → authClient.signOut()
   │  POST /api/auth/sign-out
   ▼
Better Auth:
   │ 1. delete the session row
   │ 2. clear session_token + session_data cookies
   ▼
200 → toast + router.push("/") + router.refresh()
```

After sign-out the cookie is gone and the DB row is deleted, so replaying the
old cookie fails.

## 13. Flow G — Reading the session (server and client)

### Server

```ts
const session = await auth.api.getSession({ headers: await headers() });
```

Use it in server components, route handlers, and server actions. It returns
`{ session, user }` or `null`.

With `cacheComponents: true` this is dynamic data, so wrap it in `<Suspense>`
(as `page.tsx` does) or the build complains.

### Client

```ts
const { data: session, isPending, error } = authClient.useSession();
```

Not used yet, but available for client-only widgets. It calls
`GET /api/auth/get-session` and benefits from the 60 s cookie cache.

### Cookie cache trade-off

- `maxAge: 60` means a revoked session can still look valid for up to 60 s in
  the cache. Lower it if you need faster revocation; raise it to cut DB reads.
- Sensitive actions should still check the database.

## 14. Flow H — Redirects and route protection

| Layer | What it protects |
|---|---|
| `proxy.ts` | `/auth/login` only: logged-in users are sent to `/`. |
| Server components | Read the session; render different UI. |
| Route handlers / actions | Must call `getSession` themselves before acting. |
| Better Auth | Origin/CSRF checks on POSTs and on `callbackURL` values. |

`callbackURL` is validated against `trustedOrigins`; relative paths like `/`
are allowed. An untrusted absolute URL returns `403 INVALID_CALLBACK_URL`.

Do not rely on Proxy for authorization — Next's own docs call it an
"optimistic check". Always verify again where the data is used.

## 15. Error map

| Where | Status / code | Meaning | Handled in |
|---|---|---|---|
| Arcjet | `403` empty body | Bot / shield denial | UI shows generic error |
| Arcjet | `429` empty body | Rate limit (sign-up `10/10m`, others `60/1m`) | UI shows generic error |
| Arcjet | `400` `{ message }` | Disposable / invalid / no-MX email | Inline + toast |
| Better Auth | `401 INVALID_EMAIL_OR_PASSWORD` | Wrong credentials | Inline + toast |
| Better Auth | `403 EMAIL_NOT_VERIFIED` | Password user not verified; a new email is sent | "Verify your email" message |
| Better Auth | `403 INVALID_ORIGIN` | Origin not in `trustedOrigins` | Console; add the origin |
| Better Auth | `403 INVALID_CALLBACK_URL` | `callbackURL` not trusted | Use a relative path or add the origin |
| Better Auth | `422 USER_ALREADY_EXISTS…` | Only when the generic duplicate response is off | Sign in instead |
| Better Auth | OAuth `account_not_linked` | Existing user unverified | Verify the email first |
| Verify link | `?error=TOKEN_EXPIRED` / `INVALID_TOKEN` | Old/tampered link | Request a new one |
| Reset form | `INVALID_TOKEN` | Old/tampered reset link | Request a new one |
| Email | `Failed to send email …` | SMTP down / misconfigured | See `Docs/4-configration-for-mail.md` |

## 16. Security model

| Concern | How it is handled |
|---|---|
| Password storage | scrypt hash in `account.password`, never plain text |
| Session theft | `HttpOnly` + signed cookie; `Secure` + `__Secure-` prefix in prod |
| CSRF | Better Auth validates `Origin`/`Referer` on POSTs that carry cookies; `SameSite=Lax` |
| Open redirects | `callbackURL`/`redirectTo` validated against `trustedOrigins` |
| Account enumeration | Generic duplicate sign-up response; generic password-reset response |
| Brute force / spam | Arcjet rate limits, bot detection, disposable/no-MX email blocking |
| Email spoofing | Verification JWT signed with `BETTER_AUTH_SECRET`; short expiry |
| Account takeover via linking | Auto-link only for trusted providers **and** verified local users |
| Secret leakage | `BETTER_AUTH_SECRET` server-only; never `NEXT_PUBLIC_` |
| Session revocation | DB row deleted on sign-out / user deletion; password reset only if `revokeSessionsOnPasswordReset`; 60 s cache window |

## 17. Development vs production

| | Development | Production |
|---|---|---|
| `BETTER_AUTH_URL` | `http://localhost:3000` | `https://yourdomain.com` |
| Cookies | no `Secure`, no prefix | `Secure`, `__Secure-` prefix |
| `trustedOrigins` | defaults to localhost | add every real domain |
| Email | Mailpit (`127.0.0.1:1025`) | Postal or managed SMTP |
| Verification links | printed in terminal + Mailpit | real inbox |
| OAuth apps | dev callback URLs | separate prod apps/URLs |

## 19. Gotchas specific to this repo

1. **Existing email = fake success.** `requireEmailVerification` turns duplicate
   sign-ups into a `200` with a synthetic user and no email. Always test with a
   fresh address.
2. **`403` with an empty body is Arcjet**, not Better Auth. Check the terminal.
3. **`nextCookies()` must stay last** in `plugins`. Moving it breaks cookies in
   server actions.
4. **`src/lib/auth.ts` imports `@/db`.** The Better Auth CLI
   (`npm run auth:generate`) runs outside Next and may fail to resolve the
   alias. Use `../db` there if generation breaks.
5. **`src/db/index.ts` imports only `./schema/auth-schema`.** If you add your
   own tables, switch it to `./schema` so the adapter sees everything.
6. **Sign-up does not sign you in.** With verification required, `token` is
   `null`; do not `router.push("/")` after sign-up.
7. **`router.refresh()` is required** after client sign-in/sign-out because the
   home page is a server component.
8. **Changing `BETTER_AUTH_URL` changes cookie security.** HTTPS → `Secure` +
   `__Secure-` prefix; a mismatch with the real origin breaks login.
9. **Proxy only matches `/auth/login`.** Other routes are not protected; check
   the session where you use the data.
10. **The 60 s session cache can hide a revoked session** for up to a minute.

## 21. TL;DR

1. The browser calls `/api/auth/*` through `authClient`.
2. Arcjet filters POSTs (bots, rate limits, bad emails) before Better Auth.
3. Better Auth writes `user` / `account` / `session` rows via Drizzle.
4. It sets a **signed, HttpOnly** session cookie plus a 60 s cache cookie.
5. Email verification and password reset use **signed JWTs** sent by
   `src/lib/email.ts` through SMTP.
6. Server components read the session with
   `auth.api.getSession({ headers: await headers() })`.
7. `proxy.ts` only redirects logged-in users away from `/auth/login`.
8. Sign-out deletes the DB session and clears the cookies.

That is the whole loop: **UI → route handler → Arcjet → Better Auth → Drizzle →
Postgres → cookies → server components**.
